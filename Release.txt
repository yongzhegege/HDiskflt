## Version 2.2.1 (2026-06-27)
## 版本 2.2.1 (2026-06-27)

### Bug Fixes
### 修复内容

#### 1. Fix protect_Volume resource locking order issue
#### 1. 修复 protect_Volume 资源锁定顺序错误
**Problem**:
**问题描述**：
- Original code checks `volInfo->isValid` before acquiring lock, but `isValid` can be modified by other threads between check and lock acquisition
- 原代码先检查 `volInfo->isValid` 再加锁，但 `isValid` 可能在检查后被其他线程修改
- Race condition may cause access to released resources or deadlock
- 存在竞态条件，可能导致访问已释放的资源或死锁

**Root Cause**:
**根本原因**：
- Lock is initialized in `flt_initVolumeLogicBitMap`, so lock is not initialized when `isValid` is FALSE
- 锁是在 `flt_initVolumeLogicBitMap` 中初始化的，`isValid` 为 FALSE 时锁未初始化
- If we acquire lock first then check `isValid`, accessing uninitialized lock causes system crash
- 如果先获取锁再检查 `isValid`，会访问未初始化的锁导致系统崩溃
- If we check `isValid` first then acquire lock, `isValid` may be modified in the time window
- 如果先检查 `isValid` 再加锁，在检查和加锁之间的时间窗口内，`isValid` 可能被其他线程修改

**Fix**:
**修复内容**：
- Use Double-Checked Locking Pattern
- 使用双重检查锁定模式（Double-Checked Locking Pattern）
- First check `isValid` without lock to avoid acquiring uninitialized lock
- 第一次不加锁检查 `isValid`，避免获取未初始化的锁
- Check `isValid` again after acquiring lock to prevent race condition
- 获取锁后再次检查 `isValid`，防止竞态条件
- If second check finds `isValid` changed to FALSE, release lock and return error
- 如果第二次检查发现 `isValid` 变为 FALSE，释放锁并返回错误

## Version 2.2.0 (2026-06-27)
## 版本 2.2.0 (2026-06-27)

### Bug Fixes
### 修复内容

#### 1. Fix slow boot after protection mode switch (welcome screen spinning)
#### 1. 修复保护状态切换后启动慢（欢迎画面转圈）问题
**Problem**:
**问题描述**：
- Switching from protected mode to unprotected mode causes long welcome screen spinning on first boot
- 从保护模式切到禁用保护模式，第一次进系统会长时间在帐号登陆欢迎画面一直转圈
- Takes a long time to enter desktop
- 需要很长时间才能进入桌面
- Force reboot allows quick normal boot
- 强制重启可以快速正常进入桌面
- Multiple protection switches also cause slow boot in protected mode
- 多次切换保护与禁用保护后，保护模式也会出现登陆欢迎画面转圈

**Root Cause Analysis**:
**根本原因分析**：
1. **IOCTL_WRITE_CONFIG not syncing memory state**
1. **IOCTL_WRITE_CONFIG 不同步更新内存状态**
   - Config written to sector 62 successfully, but `_protectInfo` and `_volumeList[i].isProtect` in driver memory not updated
   - 配置写入扇区62成功，但驱动内存中的 `_protectInfo` 和 `_volumeList[i].isProtect` 没有更新
   - Causes config and runtime state inconsistency
   - 导致配置和运行时状态不一致
   - After reboot, driver reads config from sector 62, but timing issues may cause reading old config
   - 重启后驱动从扇区62读取配置，但如果写入时序有问题，可能读到旧配置

2. **Bitmap initialization blocks boot**
2. **位图初始化阻塞启动**
   - `flt_initVolumeLogicBitMap` needs to iterate all clusters to build free sector bitmap
   - `flt_initVolumeLogicBitMap` 需要遍历所有簇构建空闲扇区位图
   - This process can take seconds to tens of seconds on large disks (1TB+)
   - 大磁盘（1TB+）上这个过程可能需要几秒到几十秒
   - Synchronous execution blocks system boot process
   - 同步执行阻塞系统启动流程

3. **I/O anomalies caused by state inconsistency**
3. **状态不一致导致的 I/O 异常**
   - When protection is off but bitmap still exists, read/write paths may incorrectly use redirect mapping
   - 保护关闭但位图仍在时，读写路径可能错误地使用重定向映射
   - Causes severe system I/O performance degradation
   - 导致系统 I/O 性能严重下降

**Fix**:
**修复内容**：
- **IOCTL_WRITE_CONFIG sync memory state**
- **IOCTL_WRITE_CONFIG 同步更新内存状态**
  - Update `_protectInfo` after successfully writing to sector 62
  - 写入扇区62成功后，同步更新 `_protectInfo`
  - Call `protect_Volume()` to update protection state for each volume based on new config
  - 根据新配置调用 `protect_Volume()` 更新各卷的保护状态
  - Ensure memory state matches disk config
  - 确保内存状态和磁盘配置一致

- **Add detailed performance logging**
- **添加详细的性能日志**
  - Add total time logging for `flt_initializeVolume`
  - `flt_initializeVolume` 添加总耗时日志
  - Phase timing for each volume initialization (GetVolumeInfo, InitBitmap)
  - 各卷初始化分阶段计时（GetVolumeInfo、InitBitmap）
  - Phase timing for bitmap initialization (bootstat.dat, pagefile.sys, hiberfil.sys)
  - 位图初始化各阶段计时（bootstat.dat、pagefile.sys、hiberfil.sys）
  - Helps identify specific bottlenecks causing slow boot
  - 方便后续定位启动慢的具体瓶颈

- **State consistency check** (added in v2.1.0)
- **状态一致性检查**（v2.1.0 已添加）
  - Check `isProtect` at beginning of `getRealSectorForRead` and `getRealSectorForWrite`
  - `getRealSectorForRead` 和 `getRealSectorForWrite` 开头检查 `isProtect`
  - Return original sector directly when protection is off, no mapping used
  - 保护关闭时直接返回原始扇区，不使用任何映射

## Version 2.1.0 (2026-06-27)
## 版本 2.1.0 (2026-06-27)

### Bug Fixes
### 修复内容

#### 1. Fix system instability caused by repeated protection state switching
#### 1. 修复反复切换保护状态导致系统不稳定问题
**Problem**:
**问题描述**：
- Repeated switching between enabling and disabling protection causes system instability
- 反复多次开启保护和禁用保护切换，系统容易出现不稳定
- System may require disk scan to boot
- 需要扫描磁盘才能进入
- System may black screen and fail to boot, requiring multiple reboots
- 直接黑屏无法进入系统，多次重启才可以进入

**Fix**:
**修复内容**：
- Refactor `protect_Volume` function, add ERESOURCE lock to prevent race conditions
- 重构 `protect_Volume` 函数，添加 ERESOURCE 锁防止竞态
- Clean up redirect mapping table and bitmap when protection is disabled
- 保护关闭时清理重定向映射表和位图
- Add state consistency check in `getRealSectorForRead`/`getRealSectorForWrite`
- 在 `getRealSectorForRead`/`getRealSectorForWrite` 添加状态一致性检查

**Modified Files**:
**修改的文件**：
- `sys/diskflt.c`
